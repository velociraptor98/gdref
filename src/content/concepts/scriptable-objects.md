Both engines have the same answer to "data that is not a scene object": a
standalone asset, authored in the editor, referenced by many scene objects,
carrying no transform and no lifecycle.

This is one of the closest conceptual matches in the whole reference, and one of
the least obvious — Godot's `Resource` is usually introduced as "the thing
textures and meshes are", not as "Godot's ScriptableObject".

## Sharing and the runtime-edit trap

Both are shared by reference. Two objects pointing at the same asset see one set
of values, and mutating it at runtime affects every user.

Both also persist editor-time runtime edits back into the asset, which
routinely surprises people: tweaking a value in play mode changes it
permanently. The defence in both engines is the same — treat these as read-only
at runtime, and copy when you need per-instance state.

Godot gives you two tools for that copy:

- **`resource_local_to_scene = true`** — each scene instantiating this resource
  gets its own copy automatically. No Unity equivalent.
- **`.duplicate()`** — an explicit copy, the analogue of `Instantiate(so)`.

## Text format is a real advantage

`.tres` is human-readable. It diffs in a pull request, merges when two people
edit different fields, and can be generated by scripts without the editor.
Unity's `.asset` is YAML but is dense enough that this rarely works in practice.

For data-heavy projects — item tables, dialogue, balance numbers — this changes
how the team works, not just how the file is stored.

## Resources go further than ScriptableObjects

A `Resource` can be exported inside another `Resource`, so configuration trees
nest naturally. They can carry methods, so behaviour-as-data patterns (a damage
formula as an assignable resource) are idiomatic. And because meshes, textures,
audio and scenes are *all* resources, the same reference machinery covers your
custom data and the engine's built-in assets.
